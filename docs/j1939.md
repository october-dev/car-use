# Trucks and machines: J1939

Trucks, buses, truck-mounted cranes, excavators, tractors and generator sets mostly don't speak OBD-II. Their ECUs talk SAE J1939: 29-bit CAN ids, usually at 250 kbit/s (500 kbit/s on some newer machines), on a 9-pin Deutsch diagnostic connector instead of the OBD-II socket.

J1939 makes reading easier than car CAN in one way. Each message is a Parameter Group Number (PGN), and each value inside it is a Suspect Parameter Number (SPN) at a fixed position with a fixed scale. Engine speed is SPN 190 on every engine that sends it. car-use decodes a small table of these standard SPNs and the active fault codes (DM1), and it only listens: J1939 sessions are listen-only by default, so it sends nothing to the machine.

This has been tested against the simulator's virtual crane and against hand-built frames. It has **not** been tested on real heavy equipment yet. If you try it on one, please open a Port report.

## Try it without a machine

```bash
car-use can-check --sim crane-j1939
car-use record --sim crane-j1939 --decode j1939 --seconds 30
```

## On a real machine

1. Use an adapter that can listen at 250 kbit/s with 29-bit ids. OBDLink (STN chip) adapters can. You need a 9-pin Deutsch to OBD-II cable, or an adapter with a Deutsch plug.
2. Engine running, machine parked and safe. Nobody operates the machine because car-use asked them to.
3. Run:

```bash
car-use can-check --j1939                      # ELM327 protocol A: J1939, 29-bit, 250 kbit/s
car-use record --j1939 --decode j1939 --minutes 30
CAR_USE_PROTOCOL=A car-use --listen-only <<'PY'  # scripts and helpers on J1939, this run only
print(j1939())
PY
```

`--j1939` is needed because an ELM327's automatic protocol search never picks J1939; it only tries the OBD-II protocols. For a 500 kbit/s J1939 bus, try `--protocol 7` (29-bit, 500 kbit/s). car-use also recognises J1939 on its own when most ids heard are 29-bit and carry standard PGNs, whatever protocol you listened on.

## What gets decoded

| key | SPN | PGN | name | bytes | scale | offset | unit |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `engine_speed_rpm` | 190 | 61444 EEC1 | Engine Speed | 4-5 | 0.125 | 0 | rpm |
| `coolant_temp_c` | 110 | 65262 ET1 | Engine Coolant Temperature | 1 | 1 | -40 | °C |
| `oil_pressure_kpa` | 100 | 65263 EFL/P1 | Engine Oil Pressure | 4 | 4 | 0 | kPa |
| `engine_hours_h` | 247 | 65253 HOURS | Engine Total Hours of Operation | 1-4 | 0.05 | 0 | h |
| `fuel_level_pct` | 96 | 65276 DD | Fuel Level 1 | 2 | 0.4 | 0 | % |
| `fuel_rate_lph` | 183 | 65266 LFE | Engine Fuel Rate | 1-2 | 0.05 | 0 | L/h |
| `vehicle_speed_kph` | 84 | 65265 CCVS | Wheel-Based Vehicle Speed | 2-3 | 1/256 | 0 | km/h |
| `battery_v` | 168 | 65271 VEP1 | Battery Potential / Power Input 1 | 5-6 | 0.05 | 0 | V |
| `ambient_temp_c` | 171 | 65269 AMB | Ambient Air Temperature | 4-5 | 0.03125 | -273 | °C |

Bytes count from 1, as J1939 documents do, and multi-byte values are little-endian. The positions and scales follow J1939-71. We checked them against public sources that agree with each other (the FMS-Standard, CSS Electronics' J1939 guides, and the public J1939 DBC shipped as `examples/j1939.dbc` in the dbcc project); the DM1 layout matches python-can-j1939's diagnostic messages, because SAE's own documents are paid. Fuel level (SPN 96) is in the Dash Display PGN, not in LFE.

A value the machine marks as "error" (FE, FExx, FExxxxxx) or "not available" (FF...) comes back as missing (`None`, an empty cell), never as a number. That includes the reserved values above FA.

Engine hours (HOURS) is "on request" in J1939-71. Many engines broadcast it anyway, and the virtual crane does. If yours doesn't, car-use can't get it yet: asking would mean transmitting a request.

## Faults (DM1)

DM1 (PGN 65226, J1939-73) is each ECU's list of active faults, sent about once a second. For each fault car-use gives the SPN, the Failure Mode Identifier (FMI, with its standard meaning), the occurrence count, and the four lamps (MIL, red stop, amber warning, protect).

One fault fits in an 8-byte frame. Two or more need the J1939-21 transport: a BAM announcement (TP.CM) followed by data packets (TP.DT). car-use puts those packets back together per source address. If packets are lost, for example when a slow adapter overflows, the message is dropped and counted, never guessed.

An SPN that isn't in the table above is still reported by number, with its FMI. What it means depends on the engine maker's documentation.

## In recordings and scripts

`record --decode j1939` writes:

- `signals.csv`: `t_unix, t_since_start`, then one column per key above. Each cell holds the latest value heard, and it is empty until the first one. At most 50 rows a second.
- `faults.csv`: `t_unix, t_since_start, source, mil, red_stop, amber_warning, protect, faults`, one row each time a source's DM1 changes.

`car-use dbc decode FOLDER --dbc j1939` decodes an earlier `can.csv` the same way.

In a script, `j1939(seconds=5)` listens and returns the signals, each with its value, unit, SPN, PGN and source address, plus DM1 per source and a flat `faults` list. `j1939(capture=listen(10))` decodes a capture you already have.

## Not yet

- The connection-mode transport (RTS/CTS). That is point-to-point, and car-use never takes part in it.
- Requests (for example, asking for HOURS or DM2, the previously active faults). They transmit, so listen-only mode refuses them.
- Proprietary PGNs, which are each maker's own layout. car-use counts them but doesn't decode them.
- The older DM1 SPN conversion methods. Only the current one (CM = 0) is decoded.
- CANopen and ISOBUS.
